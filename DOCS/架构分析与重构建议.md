# 架构分析与重构建议

> 适用版本：UTscan v2.8.4 备份仓库
> 目的：评估现有分层/解耦水平，提出可落地的重构路线（不改动当前行为，供后续演进）。
> 关联文档：[开发历程总结](开发历程总结-20260829.md)、[软件使用说明书](软件使用说明书-20260829.md)

## 1. 现状架构

### 1.1 分层总览（事实）

```
┌─────────────────────────────────────────────────────────┐
│ UI 层（WinForms）                                        │
│   MainForm (2638 行) · ScanForm · AscanForm · BScanForm  │
│   FftForm · ConnectionForm · TcgCurveEditorForm          │
├─────────────────────────────────────────────────────────┤
│ 编排/服务层                                              │
│   ScanService(694) · UpdateService · AuthService         │
│   ConfigService · HardwareProbeService · LinkDiagnostics │
│   Imaging(BScan/CScan) · SignalProcessing(Gate/Fft/…)    │
├─────────────────────────────────────────────────────────┤
│ 核心抽象层（Core）                                       │
│   Interfaces(3) · Models(12) · AscanFramePool · TcgCurve │
├─────────────────────────────────────────────────────────┤
│ 硬件实现层（Hardware）                                   │
│   SpectrumDaqCard / ZmcMotionController / Dpr500Controller│
│   + Native P/Invoke 封装（SpectrumNative/ZmcNative/JsrNative）│
│   Mock 三件套                                            │
└─────────────────────────────────────────────────────────┘
```

### 1.2 现状优点（已做对的部分）

1. **接口抽象到位**：三硬件接口（IDataAcquisition/IMotionController/IPulseGenerator）隔离上层与具体硬件，Mock 双实现同接口——这是最核心的解耦资产；
2. **数据管线加固**：AscanFramePool 所有权契约（克隆发布）+ `_frameLock` 串行化，并发正确性有保障；
3. **安全策略清晰**：fail-closed 装配、急停回滚、发射默认关闭、保留 IO 校验；
4. **配置单点**：hardware.json 单一来源，JsonDocument 最小化回写。

### 1.3 现状问题（耦合点清单）

| # | 耦合 | 证据 | 影响 |
|---|---|---|---|
| C1 | **MainForm 巨型类** | 2638 行，持 6 依赖（_motion/_daq/_pulse/_scanEngine/_auth/_config）+ 布局 + 事件 + 连接 + 更新 | 难测试、难演进、单文件冲突 |
| C2 | **UI 与具体实现耦合** | 10 处 `is SpectrumDaqCard`/`is ZmcMotionController`/`is Dpr500Controller` 类型检查 | 换硬件需同步改 UI（见移植说明 §5.1.2） |
| C3 | **无 DI 容器** | 全项目无 IServiceCollection；Program.cs(279 行) 手工装配 | 依赖显式但装配脆；测试替换难 |
| C4 | **连接逻辑内聚于 MainForm** | 探测/连接/回滚/状态标签 全在 OnLoad + BeginConnectSequence | 连接编排无法脱离 UI 复用 |
| C5 | **配置加载在 Program.cs** | LoadHardwareConfig 静态；SaveHardwareConfigSampleParams 静态 | 配置服务与装配纠缠 |
| C6 | **扫描状态与 UI 混合** | ScanForm(1049) 直接订阅 PointDataReady/维护 _matrix | 成像数据与窗体生命周期耦合 |
| C7 | **日志通道分散** | Debug.WriteLine（DEBUG 裁剪）+ 文件日志（Log）双通道 | 诊断埋点依赖编译符号 |

## 2. 分层/解耦改进方案

### 2.1 目标架构

```
┌────────────────────────────────────────────┐
│ 表现层（WinForms）                          │
│   MainForm → 轻量协调器（瘦身：仅菜单/DI）   │
│   ScanForm → 依赖 ViewModel/服务，不持硬件   │
├────────────────────────────────────────────┤
│ 应用服务层（可单测）                        │
│   ConnectionOrchestrator（连接编排）         │
│   ScanCoordinator（扫查协调，替代 UI 订阅）  │
│   DiagnosticReporter（诊断/探测）            │
├────────────────────────────────────────────┤
│ 领域/核心层                                 │
│   Interfaces · Models · 缓冲池 · TCG        │
├────────────────────────────────────────────┤
│ 基础设施层                                  │
│   Hardware 实现 + Native · Config · Logging │
└────────────────────────────────────────────┘
```

### 2.2 具体重构建议（按优先级排序）

#### R1. 引入轻量 DI（低风险，高收益）
- 用 `Microsoft.Extensions.DependencyInjection`（已有 net8.0 支持）；
- `Program.cs` 组合根：注册 `IDataAcquisition`/`IMotionController`/`IPulseGenerator`（useMock 条件注册）+ 各服务 + MainForm；
- 消除手工 `new` 链与静态配置方法；
- **验收**：Program.cs 缩减 >50%，MainForm 构造签名从 6 参数降为 `IServiceProvider` 或按需注入。

#### R2. 抽离 ConnectionOrchestrator（中风险，直接解决 C2/C4/C5）
- 新建 `Services/Connection/ConnectionOrchestrator.cs`：承载探测→连接→使能→回滚→状态汇总；
- MainForm 仅调用 `orchestrator.ConnectAsync()` 并订阅进度事件；
- 类型检查（`is SpectrumDaqCard` 等）下沉到 orchestrator 内的诊断适配器，UI 不再依赖具体类型；
- **验收**：MainForm 删除全部 10 处 `is` 检查，连接相关 400+ 行移出。

#### R3. ScanCoordinator 接管扫查状态（中风险，解决 C6）
- 将 ScanForm 的 `_matrix`/PointDataReady 订阅/断点续扫状态抽到 `Services/Scan/ScanSession.cs`；
- ScanForm 只做渲染，数据源来自 ScanSession；
- **验收**：ScanForm 减负约 300 行，扫查状态可脱离窗体测试。

#### R4. 统一日志门面（低风险）
- 新建 `Core/Logging/ILog.cs` + 文件实现（%APPDATA%\UTscan\utscan.log）；
- 保留 Debug.WriteLine 但统一走门面；诊断埋点不再依赖编译符号判断。

#### R5. 配置服务注入（低风险）
- ConfigService 承担 load/save/validate，Program.cs 移除静态配置方法；
- hardware.json 采样参数回写经 ConfigService 注入 DAQ 触发。

### 2.3 不建议做的（避免过度设计）

- ❌ 引入 MVVM 框架（WinForms 原生足够，重写风险高）；
- ❌ 全面事件溯源/消息总线（当前直接调用足够，无需中间件）；
- ❌ 将三硬件拆独立进程/微服务（x86 进程内 P/Invoke 是刚需，拆分得不偿失）。

## 3. 重构路线图（分阶段）

| 阶段 | 内容 | 风险 | 回归验证 |
|---|---|---|---|
| P1 | R1 DI + R5 配置服务 | 低 | 327 测试 + 启动冒烟 |
| P2 | R2 ConnectionOrchestrator | 中 | 真机连接三设备 + Mock 对比 |
| P3 | R3 ScanCoordinator | 中 | 断点续扫 + C 扫成像回归 |
| P4 | R4 日志门面 | 低 | 日志落盘检查 |
| P5 | 清理类型检查/静态方法 | 低 | 全量测试 |

> 每阶段独立可发布，不必一次完成；P2/P3 建议真机在场时执行。
